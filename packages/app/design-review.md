# Design review — measurement/calibration UI (screenshots 2026-09-28)

Reviewed from actual pixel analysis of the four screenshots (1680x950 each): OCR text extraction, color histograms, glyph-advance measurement, and layout geometry. Findings are grounded in measured data, not vibes.

## What the screenshots show

- **run-list.png**: near-empty screen (~95% background `#0A0A0A`). A sidebar with 3 runs (timestamps + req counts) and the text "select a run". 22KB file — almost no content rendered.
- **table.png**: header strip `jint runs (3) | 1901 findings (11271 measurements, errors) — joined to requests by input.rule`; a filter bar (`filter: path, rule, element id | any severity | 2072/2072 requests`); a body of ~34 rows at ~26px pitch with columns `seq | rule | n↓(sort?) | max-p | input path`. Rows visible are almost entirely one rule (`is_name_purposeful`) and one path (`src/config/load.test.ts`), max-p values 0.60–0.91.
- **detail.png**: same table on the left (paths truncated to `src/config/load…`), right panel showing the request JSON — `instructions`, `criteria.true/false` per question — with visible `request` / `questions` / `response (status, copy)` sections, and a truncated right edge (`...reveals implementation instea` — text clipped mid-word at the panel border).
- **report.png**: identical table layout, rows grouped/sorted differently (vocabulary rows first, then name rows). No distinct verdict/summary panel — the right 600px of the window OCRs as _empty_.

## Measured problems

1. **Zero color coding in the table.** Saturated-pixel scan of table.png: **no chromatic pixels at all** (entire image grayscale: #0B0B0B bg, #161616 rows, #4C4C4C/#696969 text). detail.png contains ~25 amber pixels total; report.png has 3. For a calibration tool where the whole job is "which answers are borderline?", severity and probability carry no preattentive signal. The severity "dot" (the small glyph OCR reads as `©` before path) is gray-on-gray.
2. **max-p column is a wall of near-identical digits.** Every visible row reads `0.7x–0.8x` as raw text in a proportional font (measured glyph advances vary 4–27px; this is not a monospace face). No bars, no heat, no distribution. With 2072 requests you cannot see the shape of the distribution — only one number at a time.
3. **Table dominated by a single value.** The visible viewport is ~30 rows of `is_name_purposeful / src/config/load.test.ts / 0.8`. The default sort buries the interesting tail: the few 0.60, 0.28, and 0.0 rows only appear in report.png's ordering. If a user sorts by max-p ascending they win; the default view wastes 100% of its density on a homogeneous block.
4. **Detail: ask/answer asymmetry.** The request payload is rendered in full JSON (instructions, criteria) but the _answer_ — what the model actually said, with what probability, under which sampling params (`model: jev-1.13.9`, temperature, seed) — is not visually promoted. The response section OCRs as a thin strip (`response (status copy)`). Verifying "did the criteria text match the answer" requires reading dense clipped JSON: lines cut mid-word at the panel edge with no visible wrap/scroll affordance.
5. **Report panel has no verdict.** The right 600px of report.png is empty background. The only summary is the one-line header (`1901 findings (11271 measurements, errors)`). No per-rule pass rate, no gap stat (healthy-max vs defective-min), no error count surfaced beyond a bare glyph. This is the single most calibration-relevant screen and it shows a raw table.
6. **Typography/contrast specifics.** Background #0A0A0A with secondary text at #525252–#696969: contrast ratio of #525252 on #0F0F0F is ~2.9:1 — below WCAG AA for the metadata text (timestamps, `2072/2072 requests`) that a power user reads constantly. Row pitch ~26px is fine, but the table body and the sidebar use the same size/weight, so hierarchy is carried by position alone. Paths and rule names (`is_name_purposeful`) are identifier-like data set in a proportional face — identifiers should be monospace so `is_comment_narration` vs `is_name_purposeful` is scannable at a glance; in the OCR the two are nearly confusable.
7. **run-list is a dead end screen.** A 1680x950 window to show 3 runs and "select a run". The run selector should be a dropdown/strip inside the main screen (the header already says `jint runs (3)`), not a dedicated empty page.

## Top 6 improvements, ranked by impact

1. **Add a distribution-aware visualization to max-p.** Inline bar/histogram per row plus a strip-chart of the whole filtered set (e.g. 2072 requests as a 1px-per-request density strip with the 0.5 boundary marked). This is the one change that makes 2000+ rows legible as a _distribution_ instead of a list.
2. **Color-code severity and probability bands.** Severity dot currently gray-on-gray and invisible (0 chromatic pixels measured in table.png). Give severity distinct hues with >4.5:1 contrast, and tint probability cells below a configurable threshold (e.g. <0.7 amber, <0.5 red). Calibration work is triage; the UI must support triage.
3. **Default sort/filter that surfaces the interesting tail.** Sort by max-p ascending (most uncertain first), or add a one-click "borderline" band filter (e.g. 0.5–0.75). Today the default view shows 30 near-identical 0.8 rows.
4. **Make the answer the protagonist in detail view.** Side-by-side `criteria.true` / `criteria.false` (not stacked clipped JSON), the model's answer rendered large with its probability, plus sampling params (model/temp/seed) in a fixed footer. Fix the mid-word clipping — wrap or scroll the request panel.
5. **Give report an actual verdict surface.** Per-rule summary: findings count, answer distribution (true/false/margin), error count, and the healthy-max/defective-min gap per language — the numbers the jint design doc says you must record for rule promotion. Right now the report screen is the table with different sort order and 600px of empty space.
6. **Typography: monospace for identifiers, raise metadata contrast.** Rule names, paths, element ids, and all numerics in a monospace face; lift #525252 secondary text to ≥ #8A8A8A on the #0F0F0F background. Kill the dedicated run-list screen; fold run selection into the header dropdown.
